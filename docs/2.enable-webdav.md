# Enable WebDAV

[Scope and roadmap](functional-spec.md)

## Code design

`src/webdav.rs` owns the service state and the child process handle. `src/rclone.rs` builds the arguments and launches the bundled binary through Rust's process API.

```rust
enum WebDavStatus {
    Stopped,
    Starting,
    Running(Endpoint),
    Failed(WebDavError),
}

fn enable() -> Result<Endpoint, WebDavError>;
fn status() -> WebDavStatus;
```

- Keep one process handle for the local service and serialize state changes. `enable` reuses the endpoint when the service is running. Requests that arrive during `Starting` can read the current state via `status`.
- Read the configured `RemoteId` and folder. Prepare the folder with rclone. Reuse the saved password or generate one from the operating system's random source. Select an available port in automatic mode.
- Start `rclone serve webdav` on loopback with the remote, folder, and dedicated configuration file. Pass each argument separately through the process API. Before saving the endpoint and transitioning to `Running`, send an authenticated `PROPFIND` request with a timeout to check readiness.
- If rclone cannot bind because the port is in use, retry with another port in automatic mode and cap the number of attempts. If the readiness check times out, the process exits early, or saving the configuration fails, stop and reap the child before recording `Failed`. If a running process exits, the monitor updates the service state based on its exit status.

Test concurrent enable requests, a port in use, an incorrect password, and process exits before and after readiness.

## Processing flow

1. The dashboard requests WebDAV startup. The backend reads the connected remote and resolves a path of the form `remote:folder`. If startup is already in progress, the backend returns its status to avoid launching a second process.
2. The backend uses rclone to create the folder if needed and check access. Retries reuse the same folder.
3. The backend uses the saved port if available or selects a local port according to the configuration. It reuses saved credentials or generates a password on first setup.
4. The backend runs `rclone serve webdav` with the remote, folder, Bridge's dedicated configuration, and WebDAV credentials. The process listens on loopback by default. If the selected port becomes unavailable before rclone binds, the backend tries another port in automatic mode.
5. The backend checks that the endpoint responds to an authenticated WebDAV request. It then saves the applied configuration and returns **Running**, the actual URL, the username, and the password to the dashboard.
6. Turning off the **WebDAV** switch stops rclone. The backend also monitors unexpected exits and reports **Stopped** or the corresponding error. Turning the switch on starts the service again using the saved settings.

If folder preparation or startup fails, the backend reports which step failed and cleans up any child process it started. It keeps the folder for the next attempt.

## Local defaults

- Bridge serves the `Zotero Cloud Bridge` folder and prepares its `zotero` subfolder. The dashboard displays the base URL because Zotero appends `/zotero/`.
- The default username is `zotero`. Bridge stores the generated password with its WebDAV settings in the private `webdav.json` file and passes the credentials through the rclone child's environment.
- Startup is manual. Bridge stops rclone on shutdown. Turn on the **WebDAV** switch to retry after a failure. Turn it off before changing the cloud provider so only one process can update the active rclone configuration.
- In automatic mode Bridge tries the last working port first. If the port is occupied, it retries once with a port assigned by the operating system. [Advanced settings](4.advanced-settings.md) can require a specific port. The dashboard prompts the user to update Zotero when the URL changes.
