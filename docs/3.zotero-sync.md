# Configure Zotero and verify sync

[Scope and roadmap](functional-spec.md)

## Code design

`src/sync_check.rs` lists cloud objects for the dashboard. Attachment sync runs directly between Zotero, rclone's WebDAV endpoint, and the cloud provider. The Rust backend handles status requests and remote queries.

```rust
struct RemoteObject {
    path: String,
    size_bytes: u64,
}

fn list_sync_objects() -> Result<Vec<RemoteObject>, SyncCheckError>;
```

- `list_sync_objects` reads from the same remote and folder that WebDAV serves. Run `rclone lsjson` against the target folder using the dedicated configuration, parse the JSON, and convert each object to a `RemoteObject`. Return distinct errors for access failures and timeouts. An empty list is valid.
- The proposed check takes a listing before the user imports a test PDF and another after sync. The dashboard displays newly observed paths for comparison. If several objects appear, show them as candidates until the matching method is settled.
- Read the process state via `webdav::status` and query the cloud separately. If rclone buffers writes, the user may need to repeat the check after rclone uploads the data.
- Zotero initiates downloads, updates, and file cleanup. Integration tests use two test profiles and compare downloaded file contents. To verify deletion, wait for Zotero to send the cleanup request and then query the remote again.

## Processing flow

1. The user enters the dashboard URL, username, and password under **Settings → Account → File Syncing → My Library → WebDAV** in Zotero and selects **Verify Server**. Zotero appends `/zotero/`. The settings category is named **Sync** in older versions. Zotero sends verification requests to the endpoint. rclone authenticates the requests and handles WebDAV operations against the configured cloud folder.
2. When the user imports and syncs a PDF, Zotero prepares the attachment sync data and sends it over WebDAV. rclone writes the corresponding objects to the remote. Zotero continues to send library data through the Zotero sync service.
3. When another Zotero profile using the same library needs a local copy of the PDF, Zotero reads the attachment data over WebDAV. rclone retrieves it from the remote and returns it to Zotero.
4. When the PDF changes, Zotero determines when to upload the update. rclone forwards the write to the remote. When Zotero sends a deletion request during WebDAV cleanup, rclone deletes the corresponding remote data.
5. To verify a test upload, the user requests a cloud folder check from the dashboard. The backend lists objects directly from the remote. The dashboard displays the results, including any access error. The WebDAV process state and the cloud query result are tracked independently.

## End-to-end verification

Run **Verify Server**, upload a new PDF, download it from a Zotero test profile with no local copy, change the file and download it again, then verify deletion after Zotero completes WebDAV cleanup. Repeat for each provider. Compare PDF contents for downloads and updates. Query the remote directly to verify upload and deletion.

## Verification behavior

- **Capture baseline** stores the current set of paths in the current dashboard tab. **Check cloud folder** lists paths and sizes directly from the configured remote. New paths are candidates because the object names are assigned by Zotero.
- rclone serves WebDAV with its default VFS cache mode (`off`). After Zotero finishes syncing, check the folder again if no new paths appear. Verify an update by comparing the downloaded bytes from the second profile. To verify cleanup, check that the relevant paths disappear from the listing after Zotero sends its cleanup requests.
