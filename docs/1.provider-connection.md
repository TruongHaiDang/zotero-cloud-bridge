# Connect Google Drive or OneDrive from the dashboard

[Scope and roadmap](functional-spec.md)

## Dashboard flow

1. Open **Cloud provider**, select **Google Drive** or **OneDrive**, then click **Connect**.
2. rclone opens the provider's sign-in and consent flow in the local browser. Complete authorization and return to the dashboard, which shows **Waiting for authorization** while rclone is waiting.
3. For Google Drive, the proposed initial flow uses **My Drive**. For OneDrive, choose the drive when prompted and confirm the selection.
4. After the backend verifies access and saves the connection, the dashboard shows **Connected** and enables the **Enable WebDAV** action. That action prepares the storage folder and starts the WebDAV service.

## Dashboard and Rust handoff

`src/dashboard.rs` calls `src/provider.rs` for three actions.

| Dashboard action | Backend operation |
| --- | --- |
| Click **Connect** | `begin_connect(provider)` creates a session, starts a worker, and returns a session ID. |
| Poll connection status | `connect_status(session_id)` returns the current phase, any pending question, or the final result. |
| Answer a question or cancel | `answer_connect(session_id, question_id, value)` queues the answer for the current step. `cancel_connect(session_id)` stops the worker and cleans up its temporary config. |

The session stores the provider, temporary config path, pending question, opaque rclone continuation state, and deadline. The dashboard receives display labels and question IDs. The worker retains the rclone state, process handle, and cloud credentials. Validate answers against the pending question and accept each question ID once so retries cannot advance the flow twice.

## How Rust drives rclone

1. Create a private temporary rclone config for the session. Generate the remote name server-side. The examples below use `bridge` as the remote name and `SESSION_CONFIG` as a placeholder for the temporary path.
2. Launch the bundled binary using `std::process::Command`. For Google Drive, start with the proposed read/write scope shown below. For OneDrive, start with the backend defaults.

   ```sh
   rclone config create bridge drive scope=drive --non-interactive --config SESSION_CONFIG
   rclone config create bridge onedrive --non-interactive --config SESSION_CONFIG
   ```

3. Parse stdout as JSON with `State`, `Option`, and `Error`. A nonempty `State` identifies a continuation. Use `Option.Name` to dispatch known steps and `Option.Examples` to obtain the real values and labels of choices. Reject unexpected steps with a setup error. Treat `State` as opaque and keep it on the backend.
4. Continue each step with the same config file, the returned state, and the selected value. Carry forward any configured defaults, such as `scope=drive` for Google Drive. For example, to tell rclone to use the local browser for Google authorization:

   ```sh
   rclone config update bridge scope=drive --continue --state STATE --result true --config SESSION_CONFIG
   ```

   When the question is `config_is_local`, Bridge answers `true`. That continuation runs in the worker while rclone opens the browser and waits on its loopback OAuth callback. rclone exchanges the authorization code and writes credentials into the temporary configuration. The dashboard polls the worker for the next step. rclone handles the provider callback itself.

   The worker uses stdout for rclone's JSON configuration steps. The dashboard receives the session status and any follow-up questions. The sign-in URL is opened by rclone and is never returned to the dashboard.
5. Process provider-specific questions using the JSON returned by the bundled rclone version.

   | Provider | Question handling |
   | --- | --- |
   | Google Drive | `config_shared_client_id` can appear before OAuth if using rclone's built-in client. Surface the prompt if present. Answer `false` to `config_change_team_drive` when it appears in the proposed My Drive flow. |
   | OneDrive | For `config_type`, select the `onedrive` option for a personal or business OneDrive. For `config_driveid`, show the returned choices and send the selected drive ID back to rclone. Show the confirmation for the selected drive when requested. |

6. When a successful rclone response has an empty `State`, run a direct access check against the staged remote, for example `rclone lsd bridge: --config SESSION_CONFIG`. On success, save the validated remote to Bridge's dedicated rclone configuration and return its `RemoteId` for WebDAV. Serialize updates to the dedicated config and preserve the active remote if authorization, validation, or persistence fails.
7. On cancellation, timeout, or process failure, stop and reap any child process and discard the temporary configuration. Surface the failed step without exposing tokens. Show **Reconnect required** when rclone indicates that the provider requires new authorization. Treat temporary network failures as retryable access errors.

## Review and verification

- Decide whether the app will use rclone's built-in OAuth clients or registered clients for release, which scopes it will request, and where the token-bearing configuration will be stored on macOS. The Google command above assumes the broad `drive` scope for the proposed flow.
- The initial non-interactive command was checked with rclone v1.76.0. Google Drive returned `config_shared_client_id` and OneDrive returned `config_is_local`. Live consent, drive selection, and saving a working connection still need integration tests with the actual bundled binary.
